## [Unreleased]

### Added — `pipedrive-integration` (branch-only — NOT deployed; no `clasp push`; pending live config)
- **Pipedrive API integration — push a finalized run to Pipedrive as a deal with per-type product line items** (Code.gs Section 31; `ViewRules.html`, `ViewRun.html`, `ViewVinLog.html`, and the new global `ViewPipedriveSettings.html`). Realizes to-do #5. The push is a **separate, explicit step taken AFTER in-system finalization** — never automatic, and never before the run's RUN_LOG row (with its Deal ID in col D) exists.
  - **Secrets in ScriptProperties, never in the repo or a sheet.** `PD_API_TOKEN`, `PD_COMPANY_DOMAIN`, `PD_DEFAULT_PIPELINE_ID` / `_STAGE_ID` / `_CURRENCY` (read by `pdGetSecrets_`). `setupPipedriveSecrets(token, domain, pipelineId, stageId, currency)` validates the token+domain with a live `GET /users/me` **before** saving (nothing persisted on failure); `getPipedriveStatus()` returns connection state for the UI and **never echoes the token**.
  - **Deal-field mapping is now GLOBAL (v2), not per-dealer.** A new **`PIPEDRIVE_SETTINGS`** key/value tab in SF_DEALER_CONFIG holds the global rules under row `deal_field_rules` (JSON array). Each rule sets one deal field in one of two **modes**: **copy** — `{id, deal_field, type, mode:"copy", org_field, option_map?}` (the old per-dealer `field_map` behavior: read the org's custom field and copy it to the deal field); or **conditional** — `{id, deal_field, type, mode:"conditional", group, then_value, else_value}`, i.e. *IF (AND/OR conditions on the org's fields) THEN deal field = `then_value` ELSE `else_value`*. `group` is the same shape as targeting rules (`{match:"all"|"any", children:[{field,op,values}|nested]}`) but `field` is a **Pipedrive org-field key**. Server: `getPipedriveGlobalRules_`/`getPipedriveGlobalSettings`/`savePipedriveGlobalSettings` (assigns stable `id`s so overrides keep referencing the right rule), bootstrap `getPipedriveSettingsBootstrap(refresh)`; tab auto-created by `getOrCreatePipedriveSettingsSheet_`.
  - **New org-condition engine — a PARALLEL mirror of the targeting engine, on org fields.** `pdOrgConditionMatches_` (leaf) + `pdOrgGroupMatches_` (recursive AND/OR) read an org's `custom_fields` by key and **fail SAFE** (unknown field/op, empty values, unparseable number, empty group → no match). It is a *separate* implementation: the production targeting engine (`conditionMatches_`/`groupMatches_`/`ruleMatches_`) is **byte-for-byte unchanged** (verified — only a comment references it). Helpers `pdOrgFieldValue_`, `pdSetDealField_` (monetary `_currency` companion), `pdCollectOrgKeys_` (walks copy `org_field` + conditional condition fields to fetch only the org keys a rule set needs).
  - **`PIPEDRIVE` tab col J repurposed `field_map` → `field_overrides`** (`PDCFG.FIELD_OVERRIDES`, header `field_overrides`): JSON keyed by global rule `id` → `{off:true}` (disable that global rule for this dealer/group) or a **full replacement rule** (copy|conditional, minus `id`). Resolution is `pdResolveDealFields_(orgId, globalRules, overrides, currency)` (**replaces `pdResolveFieldMap_`**): apply overrides to the global rules → evaluate the effective rule set against the org's custom fields → return the flat v1 top-level deal-field map (incl. `<key>_currency` for monetary). v1 deal custom fields are still written as **top-level hash keys**, not nested under a `custom_fields` object (that's v2-only).
  - **New `PIPEDRIVE` tab — one row per `(dealer_key, group)`**, cols A–K: `dealer_key, group, org_id, org_name, product_map` (now JSON `{type:{product_id, variation_id?}}`)`, deal_title_template, pipeline_id, stage_id, currency, field_overrides` (JSON)`, active`. A PRIMARY row plus one row per `billing_split` group — this is how Mercedes-Benz of Creve Coeur's **two Pipedrive orgs** (MB Creve Coeur + Sprinter Creve Coeur) are handled: each group row carries its own org **and** its own per-type product map. Type Rules (col O) are **unchanged**. Server: `getPipedriveDealerConfig_`, `getPipedriveDealerEditorData` (now also returns `globalRules` so the panel can list overridable rules), `savePipedriveDealerConfig` (replaces all of a dealer's rows), auto-creates the tab via `getOrCreatePipedriveSheet_`.
  - **Product variations (v2).** `product_map` values are now `{product_id, variation_id?}` (a bare id is still tolerated). New `getProductVariations(productId)` / `pdListProductVariations_` lazily fetch `GET /v1/products/{id}/variations` (variations moved to a separate endpoint — they are not embedded in the product response). `buildLineItems_(billing, productMap, products, currency, variationsByProduct)` emits `product_variation_id` and prices from the chosen variation; same product+variation across types are summed, different variations stay distinct lines. `pdAttachProducts_` sends `product_variation_id` and keys its idempotency check by **product + variation**. `pushRunToPipedrive` fetches variations only for products that actually have one chosen.
  - **Line items from billing × the group's product map.** Quantity per type = **net of dupes** (`totalNew − newDupes`, etc. from `readBillingTotals_`); types that share the same product (and variation) are summed; `item_price` resolved from the product's (or variation's) `prices[]` by currency (falls back to the first price).
  - **`pushRunToPipedrive(dealerKey, runRowIndex, mode, existingDealId)`** with `mode` = `create` | `link`. `create` makes a new deal on the group's org; `link` attaches the run's products + sets fields on a supplied existing deal (doesn't change its org). Resolves the group from the RUN_LOG note (`SPLIT:<group>` → group, else PRIMARY) and reads the correct BILLING / BILLING_<group> sheet. Deal fields now come from `pdResolveDealFields_(orgId, getPipedriveGlobalRules_(), pdCfg.fieldOverrides, currency)`.
  - **Idempotent + retry-safe (a failure never loses a run).** The Deal ID is written to **RUN_LOG col D the instant Pipedrive returns it**; a numeric col D is then treated as "deal already created" (dup guard — never a second deal). A `pd_push_<row>` ScriptProperties record tracks `productsDone`/`fieldsDone` so a retry **resumes** mid-push (no duplicate deal, no double-attach — `pdAttachProducts_` also skips products+variations already on the deal). On failure: error message + retry, no rollback.
  - **`pdFetch_` never throws** — returns `{ok, status, data, error}` (token via `?api_token=`; v1 base by default, **v2** for org custom-field reads; one bounded 429 backoff; parses `{success, data, additional_data}`). Same isolation discipline as the non-fatal stats/dashboard writes — an API failure can't fail a run.
  - **Config UI populated LIVE from Pipedrive** so PD is the single source of truth: `getPipedriveConfigBootstrap(refresh)` (products + deal/org field defs, cached ~10 min) and `searchPipedriveOrganizations(term)`.
  - **UI + nav.** New global **`ViewPipedriveSettings.html`** holds the connection setup (moved here from the Dealer Rules panel) **and** the global deal-field rules builder. The **Dealer Rules → Pipedrive panel** (`ViewRules.html`) dropped the field-map builder + connection setup (now read-only, pointing to System Settings) and gained a per-group **variation selector** and a per-field **overrides** section (Use-global / Off / Override…) whose inline replace editor **reuses a shared, context-parameterized rule-card editor** — `psRenderRuleCard_` / `psSerializeOneRule_` / `psDeserializeOneRule_` / `psRegisterRuleCtx_`, one implementation shared by both fragments. `App.html` gained a **collapsible "System Settings"** sidebar group (`toggleSettingsGroup`) housing Dealer Rules, Normalization, Data Sources, and the new Pipedrive Settings. **ViewRun** finalized cards still gain a **Push to Pipedrive** sub-block (create / link / retry, shown only **after** the card is finalized); **ViewVinLog** still has a per-run push/retry action.

### Fixed — import health (committed on `styling-updates`, pending clasp push)
- **Health baseline read is now deterministic.** Added `SpreadsheetApp.flush()` between `writeImportStats_` (which appends the current import's IMPORT_STATS rows) and `checkImportHealth_` (which immediately reads history back via `getLastRow()` + a tail window). Without the flush a stale `getLastRow()` could shift the `HEALTH_TAIL_ROWS` window and make the baseline non-deterministic. The flush sits outside both functions' try/catch so their non-fatal isolation is preserved. (Hardening surfaced while investigating a "health on merge" report — not the fix for that symptom; the merge path already computes review + health on the final merged dataset.)
- **The "Location missing from this import entirely" check now compares against only the most-recent prior import, not the whole 2,000-row history tail.** When the scraper feed renames a location (e.g. "BMW of West St Louis" → "BMW of West St. Louis"), the old name lingers in the history tail and was exact-string-flagged "missing" on *every* import forever (current data only ever carries the new name, so more data could never clear it). Now `checkImportHealth_` builds a `{timestamp: {location: true}}` map of locations that carried real inventory (`total > 0`) per prior import, finds the latest timestamp `< currentTs`, and flags a location "missing" only if it was present in *that* import but is absent now. A renamed/retired feed name ages out after one import; a genuine same-name disappearance is still caught. Only the missing-location block changed (drop/zero/missing-field checks, the non-fatal try/catch, and the 13-col read untouched); unit-tested both directions.

#### Changed — Targeting Rules: unified IF (nested AND/OR) THEN action engine (replaces `conditions`)
- **The "Targeting Conditions" table in the Dealer Rules editor is replaced by a nested rule builder.** Each rule is **IF** (conditions combined with nested **AND/OR** groups) **THEN** an *action*: **Drop on import**, **Exclude from CAO**, or **Exclude from orders**. This folds the shoehorned `drop_on_import` **operator** into a first-class **action** and lets a single rule target on multiple conditions at once (`(A AND B) OR C`). **Only that section changed** — Allowed Types, Exclude Status, Require flags, Price Range, Seasoning, the **Exclude-from-CAO pills** (`cao_exclude_types`), and Dual-Site Source Split are all untouched (the pills stay as the simple, ease-of-use path; the rule builder is the advanced path).
  - **Data model:** new **`targeting_rules`** key in `filtering_rules` (col W) — an array of `{ action, group }` where a `group` is `{ match: "all"|"any", children: [ {field, op, values} | nested group ] }`. Replaces the flat `conditions` array and its `applies_to` (now expressed as a `{type, in, […]}` condition AND'd into the group).
  - **Engine (Code.gs):** `evaluateCondition_` refactored into **`conditionMatches_`** (raw predicate) + **`groupMatches_`** (recursive AND/OR) + **`ruleMatches_`**. Polarity flips from *inclusion* ("keep if it matches") to *exclusion-on-match* ("if it matches, act"), so the predicate now **fails SAFE** (unknown field/op, empty values, unparseable number, empty group → **no match → no exclusion**), the opposite of the old fail-open — a config typo can no longer mass-exclude a dealer's inventory. New ops **`gt`/`lt`** added (the migration's `gte`→`lt` / `lte`→`gt` inversions need them); the `drop_on_import` **op** removed from `FILTER_OPS` (now `TARGETING_ACTIONS`). `applyFilteringRules_` applies `exclude_order` rules in both CAO + run phases and `exclude_cao` rules in CAO only (Bypass still overrides per run); `getImportDropLocations_`/`dropRowsOnImport_` now evaluate `drop_on_import` **action** rules through the same nested engine. `getDealerFilterRules_` returns `targetingRules` (drops `conditions`, keeps `caoExcludeTypes`); `getRulesEditorBootstrap` returns `filterActions` + `gt`/`lt` ops.
  - **UI (`ViewRules.html`):** recursive builder — client `targetingRulesModel` is the source of truth (mutate-on-edit, re-render on structural ops, Values input updates in place to preserve focus); per-rule Action dropdown, per-group ALL/ANY toggle, `+ Condition` / `+ Group`, nested removal. `FILTER_MANAGED_KEYS` swaps `conditions`→`targeting_rules` (and now lists `require_url`); a not-yet-migrated dealer's legacy `conditions` key is dropped on load so it can't round-trip as an inert passthrough.
  - **Migration (done June 17, 2026):** the **4 dealers** with a `conditions` key were rewritten — **Pundmann Ford, Bommarito Cadillac, Dave Sinclair St. Peters, Frank Leta Honda** — preserving exact behavior (incl. missing-price/year → still kept). Mazda of Columbia (only `cao_exclude_types`) untouched. **Verified live** after `clasp push`: full-sheet check confirmed 0 stale `conditions` keys and `drop_on_import` only as Frank Leta's action; 25 behavioral-equivalence assertions against the deployed engine; UI round-trip in the Dealer Rules editor. Exact before/after JSON + rollback steps: **`docs/targeting_rules_migration.md`**.

### Fixed
- **Import conflict cards were hiding the "New" column.** The VIN-conflict resolution panel showed only the *Existing* side of each conflict — the *New* column was clipped out of view, so users couldn't compare the two occurrences. Cause was a CSS regression from the 1400×900 layout rework (`0c7f126`): `#conflictList` became a 2-column grid, halving each card's width, and the `overflow:hidden` card + default `table-layout:auto` table (with a fixed 130px Field column) pushed the third column past the clipped edge. Render logic, dedupe engine, and conflict count are unchanged.

## [2026-06-12] — v2.10: Post-run finalization (deferred deal IDs + abandonable runs)

### Changed
- **RUN_LOG and ORDER_STATS are now written only at a post-run finalization step — never during the run.** `runDealer` step 17 builds self-contained `pendingRuns` entries (one per prospective log row; two for a billing-split run with group units) and returns them to the modal instead of writing rows. New `finalizeRun(dealerKey, entry, dealId)` writes one RUN_LOG (+ ORDER_STATS) row per finalized entry via the unchanged `writeRunLog_`.
  - **Invariant: no RUN_LOG row is ever written with a blank deal ID.** Finalizing requires one; enter `test` for test runs.
  - **Invariant: the VIN log is never written implicitly.** Finalizing only logs the run; the VIN log is touched solely by the explicit "✓ Add to VIN Log" button or the VIN Log Updater.
  - Motivating case: Pipedrive deals are only created once an order is known to exist — a zero-match CAO run (or the Sprinter half of an MBCC run with no vans) no longer demands a deal ID that would have to be cancelled.
- **Deal ID fields are now optional at run time for all dealers** (primary and split). They remain on the pre-run form purely to pre-fill the finalization cards; the Run button is gated on user + dealer + VINs only. Server-side required-throws removed from `pasteVinsAndRun`.
- **Post-run panel reworked into finalization cards** (DealerSelector.html): one card per prospective entry showing label + unit counts, a deal ID input (pre-filled when entered up-front), and **Finalize** / **Abandon** buttons. Cards act independently — e.g. abandon a 0-match primary and finalize the Sprinter half. "✓ Add to VIN Log" enables only once ≥1 card is finalized (0-VIN finalized rows are excluded from commit). Discard guards (confirm dialogs) protect un-finalized results on dealer change, on starting a new run, and on the Cancel/Close button. The dialog's X-close cannot be intercepted (GAS limitation) — an X-closed run is simply never logged; recovery is re-running or the VIN Log Updater's manual-entry panel.

### Added
- **`abandonRun(dealerKey, outputDocId)`** — when abandonment leaves no live cards (nothing finalized, nothing pending), the run's artifacts are deleted after a warning popup: the output doc and the dealer's `<prefix>_QR_Code_N.PNG` files are moved to **Drive trash** (recoverable 30 days, not a hard delete). A partially-abandoned split run (sibling card finalized or pending) keeps the shared doc/QRs and the abandon is bookkeeping-only — a distinct popup explains the difference.

### Fixed
