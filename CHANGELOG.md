## [Unreleased]

### Added — `pipedrive-integration` (branch-only — NOT deployed; no `clasp push`; pending live config)
- **Pipedrive API integration — push a finalized run to Pipedrive as a deal with per-type product line items** (Code.gs Section 31; `ViewRules.html`, `ViewRun.html`, `ViewVinLog.html`, and the new global `ViewPipedriveSettings.html`). Realizes to-do #5. The push is a **separate, explicit step taken AFTER in-system finalization** — never automatic, and never before the run's RUN_LOG row (with its Deal ID in col D) exists.
  - **Secrets in ScriptProperties, never in the repo or a sheet.** `PD_API_TOKEN`, `PD_COMPANY_DOMAIN`, `PD_DEFAULT_PIPELINE_ID` / `_STAGE_ID` / `_CURRENCY` (read by `pdGetSecrets_`). `setupPipedriveSecrets(token, domain, pipelineId, stageId, currency)` validates the token+domain with a live `GET /users/me` **before** saving (nothing persisted on failure); `getPipedriveStatus()` returns connection state for the UI and **never echoes the token**.
  - **Deal-field mapping is now GLOBAL (v2), not per-dealer.** A new **`PIPEDRIVE_SETTINGS`** key/value tab in SF_DEALER_CONFIG holds the global rules under row `deal_field_rules` (JSON array). Each rule sets one deal field in one of two **modes**: **copy** — `{id, deal_field, type, mode:"copy", org_field, option_map?}` (the old per-dealer `field_map` behavior: read the org's custom field and copy it to the deal field); or **conditional** — `{id, deal_field, type, mode:"conditional", group, then_value, else_value}`, i.e. *IF (AND/OR conditions on the org's fields) THEN deal field = `then_value` ELSE `else_value`*. `group` is the same shape as targeting rules (`{match:"all"|"any", children:[{field,op,values}|nested]}`) but `field` is a **Pipedrive org-field key**. Server: `getPipedriveGlobalRules_`/`getPipedriveGlobalSettings`/`savePipedriveGlobalSettings` (assigns stable `id`s so overrides keep referencing the right rule), bootstrap `getPipedriveSettingsBootstrap(refresh)`; tab auto-created by `getOrCreatePipedriveSettingsSheet_`.
  - **New org-condition engine — a PARALLEL mirror of the targeting engine, on org fields.** `pdOrgConditionMatches_` (leaf) + `pdOrgGroupMatches_` (recursive AND/OR) read an org's `custom_fields` by key and **fail SAFE** (unknown field/op, empty values, unparseable number, empty group → no match). It is a *separate* implementation: the production targeting engine (`conditionMatches_`/`groupMatches_`/`ruleMatches_`) is **byte-for-byte unchanged** (verified — only a comment references it). Helpers `pdOrgFieldValue_`, `pdSetDealField_` (monetary `_currency` companion), `pdCollectOrgKeys_` (walks copy `org_field` + conditional condition fields to fetch only the org keys a rule set needs).
  - **`PIPEDRIVE` tab col J repurposed `field_map` → `field_overrides`** (`PDCFG.FIELD_OVERRIDES`, header `field_overrides`): JSON keyed by global rule `id` → `{off:true}` (disable that global rule for this dealer/group) or a **full replacement rule** (copy|conditional, minus `id`). Resolution is `pdResolveDealFields_(orgId, globalRules, overrides, currency)` (**replaces `pdResolveFieldMap_`**): apply overrides to the global rules → evaluate the effective rule set against the org's custom fields → return the flat v1 top-level deal-field map (incl. `<key>_currency` for monetary). v1 deal custom fields are still written as **top-level hash keys**, not nested under a `custom_fields` object (that's v2-only).
  - **New `PIPEDRIVE` tab — one row per `(dealer_key, group)`**, cols A–L: `dealer_key, group, org_id, org_name, product_map` (now JSON `{type:{product_id, variation_id?}}`)`, deal_title_template, pipeline_id, stage_id, currency, field_overrides` (JSON)`, active, source_product_map` (JSON; col L — see the gross-quantities / source-split entry below). A PRIMARY row plus one row per `billing_split` group — this is how Mercedes-Benz of Creve Coeur's **two Pipedrive orgs** (MB Creve Coeur + Sprinter Creve Coeur) are handled: each group row carries its own org **and** its own per-type product map. Type Rules (col O) are **unchanged**. Server: `getPipedriveDealerConfig_`, `getPipedriveDealerEditorData` (now also returns `globalRules` so the panel can list overridable rules), `savePipedriveDealerConfig` (replaces all of a dealer's rows), auto-creates the tab via `getOrCreatePipedriveSheet_`.
  - **Product variations (v2).** `product_map` values are now `{product_id, variation_id?}` (a bare id is still tolerated). New `getProductVariations(productId)` / `pdListProductVariations_` lazily fetch `GET /api/v2/products/{id}/variations` (**v2-only** — variations are not available on v1 and are not embedded in the product response; cursor pagination). `buildLineItems_(billing, productMap, products, currency, variationsByProduct)` emits `product_variation_id` and prices from the chosen variation; same product+variation across types are summed, different variations stay distinct lines. `pdAttachProducts_` sends `product_variation_id` and keys its idempotency check by **product + variation**. `pushRunToPipedrive` fetches variations only for products that actually have one chosen.
  - **Line items from billing × the group's product map.** Quantity per type = **gross** (every matched/produced car, **including** VIN-log dupes — a re-printed VIN is still produced and billed; `totalNew`/`totalPO`/etc. from `readBillingTotals_`, no dupe subtraction); types that share the same product (and variation) are summed; `item_price` resolved from the product's (or variation's) `prices[]` by currency (falls back to the first price). *(Changed from net-of-dupes — `buildLineItems_` no longer subtracts the per-type dupe counts; applies to all dealers.)*
  - **`pushRunToPipedrive(dealerKey, runRowIndex, mode, existingDealId)`** with `mode` = `create` | `link`. `create` makes a new deal on the group's org; `link` attaches the run's products + sets fields on a supplied existing deal (doesn't change its org). Resolves the group from the RUN_LOG note (`SPLIT:<group>` → group, else PRIMARY) and reads the correct BILLING / BILLING_<group> sheet. Deal fields now come from `pdResolveDealFields_(orgId, getPipedriveGlobalRules_(), pdCfg.fieldOverrides, currency)`.
  - **Idempotent + retry-safe (a failure never loses a run).** The Deal ID is written to **RUN_LOG col D the instant Pipedrive returns it**; a numeric col D is then treated as "deal already created" (dup guard — never a second deal). A `pd_push_<row>` ScriptProperties record tracks `productsDone`/`fieldsDone` so a retry **resumes** mid-push (no duplicate deal, no double-attach — `pdAttachProducts_` also skips products+variations already on the deal). On failure: error message + retry, no rollback.
  - **`pdFetch_` never throws** — returns `{ok, status, data, error}` (token via `?api_token=`; v1 base by default, **v2** for org custom-field reads **and product variations**; one bounded 429 backoff). Treats a response as ok unless it's an HTTP error or carries an explicit `success:false`, so it handles **both** the v1 envelope (`success:true`) **and** v2 (which omits `success` and signals errors via HTTP status). Same isolation discipline as the non-fatal stats/dashboard writes — an API failure can't fail a run.
  - **Config UI populated LIVE from Pipedrive** so PD is the single source of truth: `getPipedriveConfigBootstrap(refresh)` (products + deal/org field defs, cached ~10 min) and `searchPipedriveOrganizations(term)`.
  - **Org-scoped product picker + a new global `product_org_field` setting (with auto-detection).** The per-dealer type→product dropdown previously offered the **entire** Pipedrive product catalog; it can now be scoped to the products linked to that dealer/group's **organization**. Pipedrive has **no native product↔org link** (products are a global catalog), so the link is a **product custom field** — an **Organization-type** field on the product (the user's "Customer" field) that stores the org by id. New global setting **`product_org_field`** in the `PIPEDRIVE_SETTINGS` key/value tab = the **KEY** of that product custom field (stored by key, not name; blank = unscoped, show all). **The effective field is resolved by `getEffectiveProductOrgField_()`: the explicit `product_org_field` setting if chosen, ELSE AUTO-DETECTED as the first product custom field whose `field_type` is `org`/`organization`** — so the common "we have one Customer org field" case needs **zero config** (the explicit setting only matters when there are multiple org-type product fields). Generic key/value accessors `getPipedriveSettingValue_`/`setPipedriveSettingValue_`, plus `getPipedriveProductOrgField_` (the explicit setting), `getEffectiveProductOrgField_` (explicit-or-auto-detect), and client-callable `savePipedriveProductOrgField(fieldKey)` (blank clears it → falls back to auto-detect; **busts the `pd_catalog_v2` cache** so products re-enrich). When a field is in effect, `pdListProducts_` fetches the catalog **via v2 `GET /products?custom_fields=<key>`** (v2 reliably returns the custom-field value under `custom_fields[<key>]`) and adds `customerOrgId` to each product, read from the Customer field via new `pdExtractOrgId_` (normalizes a scalar id or `{value}`/`{id}`); with **no** field in effect it stays on the v1 `/products` list. New `pdListProductFields_` / `getPipedriveProductFields()` list product custom fields for the picker; `getPipedriveConfigBootstrap` products now carry `customerOrgId` and it returns `productOrgField` (the **effective** key); `getPipedriveSettingsBootstrap` returns `productFields` + `productOrgField`. **UI:** `ViewPipedriveSettings.html` gains a **"Product → Organization field"** picker (save-on-change, with a "— none (show all products) —" option); `ViewRules.html` filters each group's product list via `pdProductVisible_(prod, groupOrgId, showAll, savedProductId)` (scoping-off / no field / no org → full catalog; an **already-saved `product_id` is ALWAYS kept**; else `customerOrgId === groupOrgId`), renders a filtered-out/missing saved product as **"Product #N (saved)"**, and adds a per-group view-only **"Show all products"** toggle (`pdSetShowAll`, not persisted). The stored mapping `{product_id, variation_id?}` is **unchanged** — only which options are offered.
  - **Bulk dealer → organization linker — a one-time, review-gated setup helper.** Links every active dealer to its Pipedrive organization in a single pass instead of hand-searching the org for each dealer. **Read-only scan:** `getDealerOrgLinkProposals()` reads all active dealers + their current PRIMARY-row org (if any), pulls all Pipedrive orgs (`pdListAllOrganizations_`), and proposes a match by name — `normalizeOrgName_` (lowercase; strip punctuation + filler words `of/the/inc/llc/co/group/automotive/auto`) + `matchOrg_` (exact-normalized → token-overlap score) — returning `[{dealerKey, dealerName, currentOrgId, currentOrgName, proposedOrgId, proposedOrgName, matchType}]` with `matchType` ∈ `exact` / `strong` (overlap ≥ 0.6) / `weak` / `none`. **Nothing is written by the scan.** **Confirmed save:** `saveDealerOrgLinks(links)` (`links = [{dealerKey, orgId, orgName}]`) upserts **only each dealer's PRIMARY-row org** — it preserves `product_map` / `field_overrides` on an existing row and creates a PRIMARY row (empty maps, `active=true`) if the dealer has none; it **never touches product mappings or any `billing_split`-group row**. **UI:** a new "Link dealers to organizations" card in `ViewPipedriveSettings.html` — **Scan & match dealers** → a review table (per row: include checkbox **defaulted on for `exact`/`strong`**, current org, proposed org with a per-row override search + a match badge) → **Save confirmed links** writes only the checked rows.
  - **Apostrophe-safe organization pickers (both the per-dealer picker and the bulk linker).** An org search result rendered with its name interpolated into an inline `onclick="…('<org name>')"` breaks when the name contains an apostrophe (e.g. **Serra Honda O'Fallon**) — the HTML parser decodes `&#39;` back to a bare `'`, which closes the JS string early and throws on click. Both pickers now **stash the search results in a JS array and pass only an integer index** to the click handler (`pdPickOrg(gid, j)` via `pdOrgResultsByGid` in `ViewRules.html`; `psLinkPickOrg(i, j)` via `psLinkOrgResultsByRow` in `ViewPipedriveSettings.html`), displaying names via `escHtml`. No name is ever interpolated into a handler argument.
  - **Deactivated-product handling — a deactivated product can never be mapped or pushed.** Pipedrive rejects a deactivated product when attaching it to a deal. (1) The catalog now flags each product `inactive` — `pdListProducts_` sets it from the v2 product's **`is_linkable === false`** (v1 fallback: `selectable === false || active_flag === false`); `is_linkable` is whether the product can be added to a deal. (2) The per-dealer product picker (`pdProductSelect_`, `ViewRules.html`) **hides `inactive` products** so they can't be newly mapped — but an **already-saved** product that's since gone inactive stays visible, flagged **"(inactive — pick a new product)"**, and is never silently dropped (kept even under the "Show all products" escape hatch, same backstop as the org-scoping preserve-already-saved rule). (3) The push **preempts before any deal is created/linked**: `buildLineItems_` carries `inactive` onto each line item (a mapped product missing from the catalog is treated as inactive too), and `pushRunToPipedrive` checks first — if any mapped product that would actually be pushed (qty > 0) is deactivated, it returns `{ok:false, stage:'inactive_product', retryable:false}` with a message naming the product(s) and pointing to **Dealer Rules → Pipedrive** to fix the mapping. **No orphaned deal is created**; the check is skipped once products are already attached (a field-only retry).
  - **Rename-safety audit (a user concern, confirmed clean).** Every Pipedrive mapping already keys on a **stable id/key, never a name:** products by `product_id`/`variation_id`, orgs by `org_id` (`org_name` is a display-only cache), deal/org custom fields by their 40-char **key**, enum / THEN/ELSE / condition values by **option id**, deals by numeric `deal_id`. So the user's product-revision workflow — **edit the ORIGINAL product to keep its product id, deactivate the duplicate** — is safe; a revision never orphans a mapping. The product dropdown's **preserve-already-saved** behavior (above) is the robustness backstop: even a deactivated/filtered-out product stays selected rather than being silently dropped on the next save.
  - **UI + nav.** New global **`ViewPipedriveSettings.html`** holds the connection setup (moved here from the Dealer Rules panel) **and** the global deal-field rules builder. The **Dealer Rules → Pipedrive panel** (`ViewRules.html`) dropped the field-map builder + connection setup (now read-only, pointing to System Settings) and gained a per-group **variation selector** and a per-field **overrides** section (Use-global / Off / Override…) whose inline replace editor **reuses a shared, context-parameterized rule-card editor** — `psRenderRuleCard_` / `psSerializeOneRule_` / `psDeserializeOneRule_` / `psRegisterRuleCtx_`, one implementation shared by both fragments. `App.html` gained a **collapsible "System Settings"** sidebar group (`toggleSettingsGroup`) housing Dealer Rules, Normalization, Data Sources, and the new Pipedrive Settings. **ViewRun** finalized cards still gain a **Push to Pipedrive** sub-block (create / link / retry, shown only **after** the card is finalized); **ViewVinLog** still has a per-run push/retry action.

### Added — `feature/pipedrive-billing-pdf` (off `pipedrive-integration` — branch-only, NOT deployed; no `clasp push`; pending one live verification)
- **Auto-generate a formatted PDF of the run's BILLING sheet and attach it to the Pipedrive deal on every push** — replacing the manual "download the CSV and attach it" step (a CSV loses all formatting, and Pipedrive's Drive attachment view can't size columns). All new in Code.gs Section 31 ("Billing PDF" subsection); **no UI/view-fragment changes**. The working BILLING sheet (`renderBillingSheet_`) is **never modified** — the PDF is built fresh in a temp tab.
  - **Best-effort / non-fatal — never fails a push.** A new **`state.billingPdfDone`** step in **`pdApplyDealContents_`** (after `designDone`), gated by a new **`runCtx` 8th param** (`{outputDocId, group, dealerName}`) threaded from both callers (`pushRunToPipedrive`, `finalizeRunNewDeal`). A failure (or a thrown error — it's wrapped in try/catch) flags **`billingPdfPending`** (returned in the push result and appended to the success message as "(billing PDF will attach on a re-push)"); the push still succeeds, and a re-push retries. Same isolation discipline as the non-fatal stats/dashboard writes. Runs on **every push — New Deal + Existing/Link**.
  - **Idempotent — one billing PDF per deal.** `pdDealHasBillingPdf_(dealId, filename)` does a `GET /files?deal_id=` and returns true if a billing PDF with the same **DATE-FREE** filename is already attached (best-effort, false on error); `attachBillingPdfToDeal_` skips if so. `billingPdfFilename_(dealerName, group)` → `Billing - <dealerName>.pdf` (PRIMARY) or `Billing - <dealerName> (<GROUP>).pdf` — filesystem-sanitized and **date-free precisely so the idempotency check matches across days**.
  - **Parser — `readBillingForPdf_(outputDoc, sheetName)`** parses the already-rendered `BILLING` / `BILLING_<group>` sheet into a structured object `{summary, byType, bySource, duplicates, dupDetail, producedVins, producedCount}` (section markers in col B, values col C, not-found list col D, the duplicate-detail table at col F, produced VINs one-per-row in col B). It **checks `DUPLICATES` before `BY TYPE`** because `── DUPLICATES BY TYPE ──` contains the substring `BY TYPE` (the same substring-trap class as CPO/CPO-EL). The URL column is dropped from the PDF.
  - **Layout — `buildBillingPdfTab_(outputDoc, data, meta)`** writes a polished vertical layout into a temp tab (`_BILLING_PDF`; a stale one is deleted first): a navy title band (dealer · Deal #id · group · date), then each section as a clean banded table (section-header bands, sub-header rows, alternating row shading, outer borders, right-aligned counts). The **produced-VINs list is a compact column-major, 6-column grid** (fill the first column top-to-bottom, then wrap into the next — newspaper-style) so it never becomes one long single column. Backgrounds/fonts/borders are applied as **batched matrices** (`setBackgrounds`/`setFontColors`/`setFontWeights`/`setFontSizes`) — one pass per push.
  - **Export — `exportSheetPdf_(spreadsheetId, gid)`** fetches the Google Sheets export URL `…/export?format=pdf&gid=<gid>&portrait=true&fitw=true&size=letter&gridlines=false&sheetnames=false&printtitle=false…` with `Authorization: Bearer ScriptApp.getOAuthToken()` → a PDF Blob (`fitw` fits to page width, preserving the sheet's formatting). **`generateBillingPdf_(outputDocId, sheetName, meta)`** orchestrates open → read → build temp tab → export by `getSheetId()` → **always delete the temp tab** (even on failure) → `{ok, blob, filename}`.
  - **Upload — `pdAttachFileToDeal_(dealId, blob, filename)`** uploads to Pipedrive `POST /api/v1/files` with an **object payload `{deal_id, file: blob}`** so GAS auto-builds `multipart/form-data` from the Blob field (a raw `UrlFetchApp.fetch` — `pdFetch_` is JSON-only). This is the **first file upload in the codebase** to the deal-attach `/files` endpoint.
  - **`attachBillingPdfToDeal_(dealId, outputDocId, group, meta)`** is the orchestrator (skip if already attached, else generate + attach). **`pdDebugBillingPdf(dealId, outputDocId, group)`** is a TEMPORARY diagnostic (run via a no-arg wrapper) to confirm the export + upload live — to be removed after verification.
  - Validated: `node --check` + **17/17 unit tests** (parser sections incl. the DUPLICATES-vs-BY-TYPE substring trap, by-source, no-dupes, filename + idempotency match). **Pending one live verification** of the Sheets PDF export-URL params + the Pipedrive `/files` multipart upload (via `pdDebugBillingPdf`).

#### Changed — `pipedrive-integration`: gross line-item quantities + per-source product config for `source_split` dealers
- **Pipedrive line-item quantity is now GROSS, not net of dupes.** `buildLineItems_` no longer subtracts the per-type VIN-log dupe counts — the quantity sent to Pipedrive for each product is **every matched/produced car, including cars flagged as duplicates because their VIN is already in the VIN log** (a re-printed VIN is still produced and billed). Applies to **all dealers**. (Was `totalNew − newDupes`, etc.; now the gross `totalNew`/`totalPO`/`totalCpo`/`totalCpoEl` read from `readBillingTotals_`.) No signature change.
- **Per-source product config for `source_split` dealers — secondary CSV output can map to its OWN Pipedrive products on the SAME deal.** A `source_split` dealer (one Location, two websites — e.g. Frank Leta's main site + AUTOLOANPRO) already produces a second CSV output on one deal; that secondary output can now be mapped to its own per-type products instead of reusing the main map.
  - **New `PIPEDRIVE` tab column L `source_product_map`** (`PDCFG.SOURCE_PRODUCT_MAP = 11`; the tab is now **cols A–L, 12 columns**): JSON `{ "<sourceGroupName>": { type: {product_id, variation_id?} } }` (e.g. `{AUTOLOANPRO: {New:{…}, PO:{…}}}`). The main-site products stay in the existing `product_map` (col E); `{}` (empty) for non-source-split dealers. Parsed/written by `pdRowToConfig_` (`sourceProductMap`) and `savePipedriveDealerConfig`; `PIPEDRIVE_HEADERS` gains `source_product_map`.
  - **Editor + UI.** `getPipedriveDealerEditorData` now also returns `sourceSplit` (from `getSourceSplit_`), and the Dealer Rules → Pipedrive panel (`ViewRules.html`) renders a **secondary per-type product grid** ("Products for the `<groupName>` output") inside each deal block **whenever the dealer has a `source_split`** — driven generically off `filtering_rules`, the same way `billing_split` drives the per-deal blocks (no per-dealer code).
  - **Push.** When a `source_split` **and** a secondary product map are both set, `pushRunToPipedrive` builds line items from `product_map × main-source qty` **plus** `source_product_map[group] × secondary-source qty` on the **one** deal, merged by product+variation. Per-source **gross** quantities come from the BILLING "BY SOURCE (QTY PER SKU)" section via new `readBillingBySource_`; helpers `bySourceToBilling_` (per-source `{type:qty}` → the billing-totals shape `buildLineItems_` reads) + `mergeLineItems_` (sum by `product_id|variation_id`). Until a secondary map is configured, the push is unchanged (main map × all vehicles). The deactivated-product preemption covers secondary products too. `renderBillingSheet_` now also writes the BY SOURCE section on a `billing_split` group sheet, so a future dealer with BOTH splits works.
  - **Generalization.** `billing_split` (separate deals, each its own org + product map — e.g. MBCC) and `source_split` (one deal, separate products per source — e.g. Frank Leta) are the two product-partition axes; the Dealer Rules → Pipedrive screen now renders the right product config for either **automatically from `filtering_rules`**, so any future dealer configured with either split needs no code change.

#### Changed — `feature/pipedrive-finalize-flow` (off `pipedrive-integration`): Run-Order finalize is now METHOD-FIRST
- **Each post-run finalization card now leads with a push-method choice, then one Finalize button — replacing the old "enter a deal ID, Finalize, THEN a separate Push to Pipedrive block" flow.** Backend in Code.gs Section 31 (+ the finalize/commit functions); UI in `ViewRun.html` (card layout) and `ViewVinLog.html` (Commit gating). This **supersedes** the v2.10 deal-id-optional-then-push model and the Pipedrive "Push to Pipedrive sub-block shown only after the card is finalized" UX described in the Pipedrive Integration entry above — the push is now invoked **from** the finalize action. A brand-new order previously had no deal ID to finalize with (the only workaround was typing the placeholder `test`); each card now offers three methods:
  - **New Deal** — `finalizeRunNewDeal(dealerKey, entry)` creates the Pipedrive deal **first** (a real numeric id — no typed deal id), then finalizes the run with that id (so the "no RUN_LOG row without a real deal id" invariant still holds, with no placeholder), then attaches products + sets fields. The deactivated-product preempt (`pdCheckInactiveProducts_` → `stage:'inactive_product'`) runs **before any deal is created**, so a bad mapping creates and logs nothing.
  - **Existing** — `finalizeRunExisting(dealerKey, entry, existingDealId)` validates the id via `pdGetDeal_` **first** (no row written for a bad id), finalizes with it, then links products via `pushRunToPipedrive(…, 'link', id)`.
  - **Test order** — `finalizeRun(dealerKey, entry, 'test')` (unchanged) — never touches Pipedrive; **now excluded from VIN-log commit** (`commitLatestRun` throws on a `test` col-D; `commitRunRows` skips it and returns `skippedTest`; the UI hides/disables Commit for test runs).
- **Method availability per card** comes from new client-callable **`getRunPushModes(dealerKey, group)` → `{test, newDeal, existing, reason}`** (Test always available; New/Existing require an active Pipedrive org config) — attached as **`pushModes`** on each `pendingRuns` entry by `runDealer` so the card renders the right controls without a round trip.
- **New-Deal idempotency anchor — a `pd_new_<outputDocId|group>` token cache** bridging the reorder. Because the deal is created **before** the RUN_LOG row exists, the usual numeric-col-D dup guard isn't available yet; so `finalizeRunNewDeal` caches the deal id (and then the `rowIndex`) in ScriptProperties under the stable run token the **instant Pipedrive returns it** — a retry that failed before/after finalize **adopts** the cached id instead of creating a 2nd deal or a 2nd row. Cleared on success (`pdNewDealCacheClear_`) alongside the row-keyed `pd_push_<row>` state. (`pushRunToPipedrive`'s own col-D dup guard + `pd_push_<row>` resume are unchanged and still cover the link/retry path.)
- **`pushRunToPipedrive` refactored into reusable helpers — NO behavior change.** Split into `pdResolveRunContext_` (config/org gate + currency + line items, read-only, incl. `source_split`), `pdResolveDealId_` (create-or-validate, persists nothing), `pdCheckInactiveProducts_`, and `pdApplyDealContents_` (attach products + set fields, idempotent via the passed `state`). `pushRunToPipedrive`'s signature, gates, and return shapes are **unchanged**, so the ViewVinLog push path (already-finalized runs) and the link/retry path are untouched; the new finalize orchestrators compose the same helpers.

## [2026-06-12] — v2.10: Post-run finalization (deferred deal IDs + abandonable runs)

### Changed
- **RUN_LOG and ORDER_STATS are now written only at a post-run finalization step — never during the run.** `runDealer` step 17 builds self-contained `pendingRuns` entries (one per prospective log row; two for a billing-split run with group units) and returns them to the modal instead of writing rows. New `finalizeRun(dealerKey, entry, dealId)` writes one RUN_LOG (+ ORDER_STATS) row per finalized entry via the unchanged `writeRunLog_`.

  - **Invariant: the VIN log is never written implicitly.** Finalizing only logs the run; the VIN log is touched solely by the explicit "✓ Add to VIN Log" button or the VIN Log Updater.

- **Deal ID fields are now optional at run time for all dealers** (primary and split). They remain on the pre-run form purely to pre-fill the finalization cards; the Run button is gated on user + dealer + VINs only. Server-side required-throws removed from `pasteVinsAndRun`.
- **Post-run panel reworked into finalization cards** (DealerSelector.html): one card per prospective entry showing label + unit counts, a deal ID input (pre-filled when entered up-front), and **Finalize** / **Abandon** buttons. Discard guards (confirm dialogs) protect un-finalized results on dealer change, on starting a new run, and on the Cancel/Close button.
